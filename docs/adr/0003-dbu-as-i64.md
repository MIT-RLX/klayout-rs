# ADR-0003 — DBU coordinates as `i64`, not `i32`

**Status:** Accepted

## Context

Database units (DBU) are the integer unit the workspace stores
coordinates in. The convention is 1 DBU = 1 nm (matching KLayout's
default). A modern reticle is ~33 mm × 26 mm = 33×10⁶ nm × 26×10⁶ nm,
so coordinates land in the ±10⁸ range; a wafer is ~3×10⁸ DBU. A
`u32` covers ±2.1×10⁹ — comfortably enough for a reticle, but
reserved coordinate space (annotation regions outside the die
shadow, error markers placed at "infinity" sentinels) and arithmetic
intermediates (Hanan-grid cross products, Manhattan-difference
sums) overflow with frightening regularity in `i32`.

KLayout's C++ engine uses `int32` and pays the price in subtle
overflow bugs at extreme coordinates. We had two options:

1. **`i32` with explicit overflow guards** at every arithmetic site
   that could legitimately produce out-of-range results. Saves 50%
   of struct memory but needs `checked_*` arithmetic everywhere.
2. **`i64` throughout.** Doubles `Point` and `Bbox` size from 8/16
   bytes to 16/32 bytes. Removes overflow concerns up to 9.2×10¹⁸
   DBU = 9.2×10⁹ m, well above any plausible silicon coordinate.

## Decision

`Point::{x, y}: i64`. `Vec2`, `Bbox`, all derived types, and every
DBU-typed field follow.

## Consequences

**Pro:**
- No silent `i32`-overflow bugs at the API boundary.
- Arithmetic intermediates (e.g. `dx * dy` for cross products) can
  be `i128` (see ADR ... for the i128 promotion policy).
- Round-trip parity with KLayout's `int64` mode (which exists for
  exactly this reason).

**Con:**
- 2× memory on every `Point` and `Bbox` field. For a 1B-shape
  layout, that's an extra ~32 GB resident vs `i32`.
- The validation corpus encodes `i64` ground truth; downgrading
  to `i32` later would be a corpus-rebake.
- `Vec<Point>` cache lines hold half as many points.

## Revisit if

- We need to handle billion-shape designs in-memory and the
  doubled `Point` size becomes the bottleneck (use
  `klayout-spatial` to keep working sets small instead of
  shrinking the struct).
- A future hardware platform makes `i32` materially faster
  (unlikely on x86_64 / aarch64).
